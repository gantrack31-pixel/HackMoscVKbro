Обнаруженных по проведённым проверкам критических поломок основного сценария нет: доступные тесты и production-сборка проходят.

Это не равнозначно гарантии отсутствия дефектов: live-интеграции и production-инфраструктура проверены не полностью. В первую очередь нужно уточнить происхождение и назначение нескольких бинарных PPTX, проверить интерфейс по доступности/реальным браузерам и устранять предупреждения совместимости Python в поддерживаемом диапазоне версий.

## Приоритетные действия

### P0 — до публичного размещения

1. **Подтвердить production-модель размещения и выполнить staging-приёмку.** Документация уже описывает HTTPS, SMTP, secure cookies, резервные копии и ограничения одно-процессной очереди. Настройки не заменяют испытание реального reverse proxy, восстановления базы и внешнего провайдера. Следовать checklist в `docs/VALIDATION.md`; критерий — успешное восстановление резервной копии и проверка основных пользовательских сценариев на staging.
2. **Инвентаризировать бинарные презентации с UUID в `backend/data/templates/`.** Пять таких PPTX отслеживаются Git; две записи имеют одинаковый Git blob SHA (`76ab…` и `c3bd…`). Это подтверждённое дублирование байтов, но не доказательство ненужности: установить владельца, назначение, лицензию и наличие ссылки из fixture/тестов, затем удалить только подтверждённые дубли.

### P1 — надёжность

3. **Сверить поддерживаемый Python с фактическим CI/окружением.** README рекомендует 3.11–3.13, локальные тесты запускались на 3.14 и дали 66 deprecation warnings. Добавить CI-матрицу поддерживаемых версий и отдельный сигнал на warnings; обновлять зависимости или код по результату матрицы, а не объявлять текущий проход доказательством поддержки 3.14.
4. **Запустить полный Playwright E2E в чистом Chromium окружении и отдельно покрыть другие целевые браузеры, если они поддерживаются.** Unit-тесты не заменяют сквозную проверку интерфейса.
5. **Сделать автоматическую визуальную регрессию экспорта.** Сейчас документация честно требует PowerPoint-проверки сложных шаблонов; контролируемые тестовые PPTX и рендер на согласованном движке помогут обнаруживать обрезание/смещение. Не сравнивать бездумно разные версии Office как пиксель-в-пиксель.

### P2 — сопровождение

6. Упростить CSS после инвентаризации селекторов и порядка импорта: есть 22 таблицы стилей, некоторые имеют заметный объём и названия, похожие на накопительные слои. Удалять только после доказательства отсутствия использования и визуальных тестов.
7. Установить происхождение и лицензию всех шаблонов и примеров; дубликаты в Git LFS/архиве или генерация образцов в CI возможны лишь после проверки workflow и требований к автономному запуску.

## Что не следует считать дефектом без дополнительных данных

- Отсутствие встроенного объекта SmartArt и графики мастера в PDF/HTML — это явно документированная граница форматов/реализации.
- Demo-режим — осознанный режим без реальной модели, он обозначен в интерфейсе и документации.
- Отсутствие OCR для сканированных PDF и отсутствие автоматической фактической верификации — известные ограничения, не скрытые обещания продукта.
- Локальная SQLite и одно-процессная очередь — текущие эксплуатационные ограничения; миграция/очередь нужны только при соответствующей модели развёртывания.
- Файлы примеров, шрифты и исходные PPTX могут быть необходимыми fixture/ресурсами; размер сам по себе не основание удалить их.

## Дополнительные подтверждённые наблюдения

- Frontend состоит из 22 CSS-файлов; `main.tsx` импортирует базовый набор, некоторые CSS также подключаются компонентами. Перед удалением нужна реальная проверка импорта и правил.
- Пять UUID-шаблонов присутствуют в Git; два файла совпадают по Git blob SHA. Неизвестно, относятся ли они к тестовым входам, загрузкам или исходным шаблонам.
- Отдельного root CI workflow в поверхностном просмотре структуры не обнаружено; список проверяемых путей следует перепроверить (`.github/workflows` и настройки хостинга) перед утверждением, что CI отсутствует.
- В `config.py` есть параметр `MAX_UPLOAD_MB`, который публикуется health API; импорт материалов независимо ограничен фиксированным пределом 5 МБ/файл и суммой 15 МБ. Нужно подтвердить, что различие задумано для разных типов загрузок, и не создавать UI, который трактует health-поле как лимит всех загрузок.
