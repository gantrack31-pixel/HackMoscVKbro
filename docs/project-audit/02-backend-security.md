# Backend и безопасность: результаты аудита

## Область проверки

FastAPI маршруты и middleware (`backend/app/main.py`), настройки (`config.py`), SQLite (`database.py`), а также защита PPTX и импорт материалов. Прочитаны имеющиеся `docs/SECURITY_REVIEW.md`, `docs/ARCHITECTURE.md`, `docs/VALIDATION.md` и соответствующие тесты.

## Подтверждённые сильные стороны

- Production-настройки валидируются до инициализации БД; внешние LLM URL ограничены HTTPS (исключение — loopback).
- Сессии/CSRF, проверка Origin, rate limits, разделение данных по владельцу и скрытие деталей validation описаны и покрыты тестами.
- Загрузка PPTX проверяет ZIP-размеры, число частей, пути, XML, relationship и повреждённые записи; для документов установлены лимиты объёма.
- Локальный backend suite: 133 passed, 1 skipped.

## Замечания и рекомендации

### BE-1. Не запускать произвольную конфигурацию из недоверенного окружения — P0 при публичном размещении

**Основание:** корректность HTTPS, секретов, почты и разрешённых origin зависит от deployment environment/reverse proxy. `docs/VALIDATION.md` прямо требует TLS, proxy rate limit, секреты и резервные копии; локальный тест не проверяет инфраструктуру.

**Риск:** небезопасная публикация сервера может раскрыть сессии, секреты или пользовательские файлы, даже если кодовые unit-тесты проходят.

**Исправление:** staging deployment с TLS, secure cookie, закрытым прямым портом приложения, ограничением запросов/загрузок на proxy, отдельным секрет-хранилищем и минимальными правами ОС. Выполнить восстановление базы и storage из зашифрованной копии.

**Готово, когда:** опубликован runbook, подтверждены восстановление и основные сценарии на staging, конфигурация прошла production validation.

### BE-2. Физические SQLite-таблицы не задают явные внешние ключи — проверить целостность — P2

**Основание:** `database.py` создаёт, например, `sessions.user_id`, `projects.user_id`, `favorites.user_id` как обычные поля; в показанной схеме не обнаружены `REFERENCES`/`PRAGMA foreign_keys`. Кодовые маршруты выполняют проверки владельца и есть тесты изоляции.

**Риск:** ошибки очистки/удаления могут оставлять сиротские строки или несогласованные записи. Не утверждается, что текущий сценарий уже создаёт сироты.

**Исправление:** сначала проверить все существующие данные и транзакции удаления/отзыва; добавить безопасные миграции FK с `ON DELETE` политикой либо регулярную проверку orphan rows. Учитывать, что SQLite требует включать `PRAGMA foreign_keys=ON` для каждого соединения.

**Готово, когда:** миграционный тест на копии старой БД, orphan audit и тесты cascade/restrict проходят без потери данных.

### BE-3. Проверить периодическую очистку rate-limit/OAuth записей — P2

**Основание:** таблицы `auth_attempts`, `support_attempts`, `oauth_states` и expiry email/reset создаются в `database.py`. Для support удаляются старые записи при обработке запроса; очистка остальных таблиц/просроченных токенов в просмотренном коде не подтверждена полностью.

**Риск:** неограниченный рост вспомогательных таблиц при долгой работе одного экземпляра.

**Исправление:** найти существующую очистку в auth-модуле; если отсутствует, добавить безопасную периодическую/пороговую задачу и индексы по времени. Не удалять активные токены/сессии.

**Готово, когда:** тест продвигает время, запускает очистку и проверяет, что старые записи удалены, действующие остаются.

### BE-4. Несколько процессов не являются поддерживаемым режимом текущих generation jobs — ограничение, не текущий баг — P0/P1 в зависимости от deployment

**Основание:** `docs/ARCHITECTURE.md` указывает на semaphore в памяти и одно-процессный запуск; Docker запускает один Uvicorn процесс. SQLite хранит задания, но локальный семафор не разделяется между worker-процессами.

**Исправление:** для одного процесса зафиксировать это в deployment checks и не включать multi-worker. Если нужны несколько реплик — вынести задания в общий брокер, добавить идемпотентность и общее хранилище.

**Готово, когда:** проверка deployment не запускает неподдерживаемую конфигурацию либо многопроцессная схема имеет интеграционные тесты.

## Не подтверждённые как дефекты гипотезы

- На основании видимых тестов не выявлено доказанного обхода изоляции аккаунтов.
- В репозитории есть уже проведённый security review и проверки загрузки; повторный внешний pentest не выполнялся.
- `MAX_UPLOAD_MB` в health и лимит импортируемых материалов — разные контексты; необходимо подтвердить семантику у каждого endpoint, а не считать их автоматически противоречием.
